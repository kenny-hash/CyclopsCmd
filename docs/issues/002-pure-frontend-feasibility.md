# 002 - 纯前端实现可行性评估

## 结论

当前应用不能仅依靠浏览器端纯前端技术栈完整实现所有现有功能。核心限制在于：浏览器无法直接发起 SSH 连接、无法安全保存服务器凭据、无法提供后端级连接池/跳板机隧道能力，也无法在 GitHub Pages 等静态托管环境中运行 FastAPI、AsyncSSH 或 SQLite 服务端逻辑。

如果目标是保留“批量 SSH 执行、跳板机、实时输出、配置持久化”这些能力，仍需要以下至少一种运行时：

- 独立后端服务，例如当前 FastAPI + AsyncSSH；
- 桌面端本地后端，例如当前 Electron sidecar；
- 浏览器插件或本地 agent，用于代替服务端执行 SSH 与本地持久化。

## 当前功能拆解

| 功能 | 当前实现 | 纯浏览器前端是否可完整实现 | 说明 |
| --- | --- | --- | --- |
| 表格录入、校验、导入导出 | React + Handsontable | 可以 | 纯 UI 和文件导入导出适合前端实现。 |
| 保存/加载配置 | FastAPI + SQLite | 部分可以 | 可以改为 LocalStorage/IndexedDB，但只能保存在当前浏览器，且不适合保存明文服务器密码。 |
| 批量执行 SSH 命令 | FastAPI + AsyncSSH | 不可以 | 浏览器没有原生 SSH/TCP socket API，不能直接连接目标服务器 22 端口并执行命令。 |
| 跳板机访问 | AsyncSSH direct-tcpip tunnel | 不可以 | 需要 SSH 隧道/TCP 转发能力，浏览器沙箱不提供。 |
| 实时输出 | FastAPI WebSocket 推送 | 部分可以 | 前端可以显示流式输出，但输出来源仍需要后端、桌面 sidecar 或本地 agent。 |
| 连接池、重试、错误分类 | FastAPI 后端 | 不可以完整实现 | 这些能力依赖服务端长期连接、SSH 异常类型和网络访问能力。 |
| GitHub Pages 静态部署 | GitHub Actions + Vite | 只能托管前端 | Pages 不能运行 FastAPI 后端，部署后仍要连接独立后端。 |

## 可选路线

### 路线 A：继续保留前后端分离

适合 Web 访问和多人使用。前端可部署到 GitHub Pages，后端部署到云服务器、容器平台或内网运维服务器。

优点：

- 最贴近当前架构；
- 能完整保留 SSH、跳板机、WebSocket、SQLite 等能力；
- 便于集中控制访问权限、审计和凭据管理。

缺点：

- 需要额外维护后端服务；
- 需要处理 CORS、HTTPS、WebSocket、鉴权和凭据安全。

### 路线 B：Electron 桌面应用

适合每个运维人员在本机运行。当前仓库已经有 Electron 桌面壳，启动时会拉起本地 FastAPI 后端作为 sidecar。

优点：

- 不需要公网后端；
- 可以访问本机网络和内网目标；
- 能完整保留现有能力。

缺点：

- 不是纯前端浏览器应用；
- 需要打包、分发和升级桌面应用。

### 路线 C：纯前端演示版

适合 GitHub Pages 展示 UI、导入导出配置、模拟执行结果。

优点：

- 部署最简单；
- 不需要后端；
- 适合演示界面和配置模板编辑。

缺点：

- 不能真实执行 SSH；
- 不能真实连接跳板机；
- 不能提供生产可用的批量运维能力。

## 建议

如果目标是“当前应用的所有功能都可用”，不建议投入纯浏览器前端改造；建议保留后端服务或继续完善 Electron sidecar 模式。

如果目标只是“在 GitHub Pages 上打开一个可体验的页面”，可以新增纯前端演示模式：

1. 保留表格、校验、配置导入导出；
2. 使用 IndexedDB 保存非敏感配置；
3. 禁用真实执行按钮或改为模拟执行；
4. 在页面上明确提示“静态演示模式不执行 SSH”。
